# factor: calculation engine research

Researched 2026-10-05 by Sage, building on `calc-tools.md` and `calc-features.json` in this folder.
Ranked for Peter's situation: solo, Rust desktop app, macOS now and Windows later, open source with
possible commercial use, multi-game.

> **Puck's note, added when filing:** "solo" and "open source with possible commercial use" are
> Sage's framing, not rulings. The licence is open (D-025 in `../decisions.md`). Being solo is
> a consideration, not the lens: a finding that was ranked down for that reason should be
> re-weighed.

**Labels.** Every claim carries one of three.
- **[observed]**: I read it myself in a primary source (repo source file, devlog, crate metadata,
  header file) or measured it.
- **[reported]**: someone else said it (forum post, issue, review aggregator, author claim).
- **[inferred]**: my own reasoning, untested.

## 0. Headline

1. **The core is an LP. MILP is a narrow add-on, and SAT is the wrong tool for rates.** Every
   rate-solving tool I read uses a continuous LP, or a square linear solve when the graph is fully
   determined. Whole machines come from rounding up after the solve, never from integer variables
   in the main model. Integer variables show up in only one place: FICSIT Planner uses binaries to
   count resource kinds. [observed, §1]
2. **The solver is not the bottleneck at Satisfactory or modded-Factorio scale (measured).**
   - The whole-game Satisfactory LP (291 machine recipes, 168 items) solves in about **1 ms** on
     HiGHS 1.15.1.
   - 300 factory copies sharing *binding* resource caps (141,600 columns, 50,413 rows) solve in
     about **0.66 s**. This is a size upper bound, not a realistic plan.
   - Factorio Space Age's whole database (870 recipes) solves in **2.2 ms**.
   - Pyanodons with Alien Life (12,347 recipes, 17,097 columns) solves in **0.81 s**.
   - [observed: measured, §2.4]
   - Proving a large LP *infeasible* took up to **19×** longer than solving a feasible one, which
     is one more reason to make the formulation elastic.
3. **Modeler is slow because of what it computes, not because of the solver or the recompute
   strategy.** Its own devlogs say so.
   - The slow mode is the "Full calculator". It reproduces in-game even-split splitter and merger
     preference, priority splitting and backpressure. The developer calls that "a surprisingly hard
     problem" that "may slow down greatly for larger builds".
   - Modeler's Manual calculators, which use conservation and ratios only, "always run quickly".
   - Its one documented speed-up was decoupling: sections separated by overflow-to-sink can be
     calculated independently.
   - [observed, §2.1]
   - So Peter's SAT hypothesis doesn't hold, and Puck's "recomputation strategy" is half right.
     Decomposition helps, but the cost driver is the semantics. **Whether factor reproduces
     in-game splitter behaviour is the first decision this research hands back (D1).**
4. **Nonlinear power isn't a solver problem once clock is a fixed parameter per recipe.** For a
   fixed clock, power is linear in rate. [inferred, derivation in §3.1] The tools that handle
   overclocking all fix clocks before the solve and compute power after it. [observed, §3.2]
   Somersloops are different. They change material flow (more output from the same input), so
   they must sit inside the solve, not in a pass after it.
5. **Rust: HiGHS through the `highs` or `good_lp` crates is the best-fitting solver.** Its licence
   is MIT. It builds on macOS and Windows CI, but needs CMake, a C++ compiler and, on Windows,
   libclang at build time. [observed, §4] Two traps:
   - `good_lp`'s **default** backend is CBC, which is EPL-2.0 and needs a system-installed library.
   - IIS and basis warm-start exist in HiGHS's C API but are **not wrapped** by the `highs` crate.

## 1. Formulation

### 1.1 How the existing tools formulate it

All rows are [observed] in source unless marked otherwise. Paths are repo-relative.

| Tool | Case | Solver | Formulation |
|---|---|---|---|
| **FactorioLab** (`factoriolab/factoriolab`, `src/solver/solver.ts`) | targets → recipes | GLPK simplex via `glpk-ts` | Continuous LP, minimising cost. One **equality** row per item, with **elastic slack columns**: surplus (−1), unproduceable (+1), excluded (+1), and input (+1, bounded), each carrying a user-tunable penalty (`costs.surplus`, …). Recipe columns are continuous. Machine counts are `step.machines.ceil()` after the solve (line 926). Modules, beacons, Somersloops and overclock are applied **before** the solve as recipe adjustments (`src/state/adjustment.ts`). Power uses `usage.mul(oc.pow(1.321928))` after the solve (line 353). |
| **YAFC-CE** (`Yafc-CE/yafc-ce`, `Yafc.Model/Model/ProductionTable.cs`) | user's table, with links | OR-Tools **GLOP** (`DataUtils.CreateSolver`, feasibility tolerance relaxed to `1e-1`) | Continuous LP. Constraints exist **only for goods the user linked**, and each link can be Match, AllowOverProduction or AllowOverConsumption. When the solve is infeasible it adds slack only on **SCC-derived deadlock candidates** and on split links (`GetInfeasibilityCandidates` → `MergeStrongConnectedComponents`), re-solves, and flags `DeadlockCandidate` / `OverproductionRequired`. `CostAnalysis.cs` runs a whole-modpack LP and reads `DualValue()`. |
| **Foreman2** (`DanielKote/Foreman2`, `Foreman/Models/Solver/*`) | **user-drawn graph** | OR-Tools GLOP | Continuous LP, **solved once per connected component** (`GraphOptimisation.cs`: `foreach (var nodeGroup in GetConnectedComponents(false))`). ### 1.2 Verdicts

- **(a) "Choose recipes and rates to hit targets" is an LP.**
  - It is continuous rates, linear balance rows and a linear objective. [inferred, and consistent
    with every tool above, observed]
  - MILP is needed only where a *count* must be whole **and** that wholeness changes what else is
    feasible. Examples:
    - a Somersloop or shard stock spread across machines;
    - "at most N resource kinds" (FICSIT's binaries);
    - blueprint copies that must be whole (Modeler's "Auto Round", [observed] in its 2025-08-26
      devlog).
  - Rounding machine counts up after the solve is exact for everything except power and building
    cost, and those are reported, not constrained. [inferred]
- **(b) "Propagate flows through a graph the user drew"** has three possible semantics, and they
  need different engines:
  1. **Conservation plus fixed ratios, with the graph fully determined.** This is a square linear
     system. A sparse LU solve handles it, loops included, with no iteration (Factory Planner's
     Gaussian engine). [observed]
  2. **Conservation plus ratios, under- or over-determined.** An LP with an objective (fewest
     buildings, least surplus) and elastic slacks (Foreman2, YAFC). This is a strict superset of
     (1). [observed]
  3. **In-game splitter and merger behaviour: even-split preference, priority, backpressure.**
     This is an equilibrium or fixed-point problem, not a single LP. It is what Modeler's Full
     calculator does, and it is the expensive one. [observed, §2.1]
     - I *suspect* it can be computed as a sequence of LPs: max-min-fair "progressive filling" for
       even splits, and a lexicographic objective for priority. [inferred, **untested**; I found
       no tool that documents doing this]
- **SAT or constraint programming are not the right core for rates.** Rates are continuous
  quantities, and SAT works on Booleans. [inferred]
  - CP does fit **physical layout**. Factorio-SAT (`R-O-C-K-E-T/Factorio-SAT`, GPL-3.0, 780
    stars) designs belt balancers by encoding tiles as Booleans. Its README warns it "gets
    exponentially harder as more splitters are added". [observed]
  - If factor ever lays out the physical layer (footprints, ports, balancers), CP is a candidate
    there. In Rust: Pumpkin (`pumpkin-solver` 0.5.0, MIT OR Apache-2.0, repo pushed 2026-10-05)
    [observed]. That is a separate engine from the rate engine.

## 2. Scale and incremental recompute

### 2.1 Why Modeler degrades: the evidence

- **Developer devlog, 2025-03-26 "Manual Calculator"** [observed, Steam `GetNewsForApp`, appid
  3187030]:
  - The Full calculator "tries to model what would happen in game and takes into account how
    splitters and mergers prefer to split/merge evenly and also takes into account how priority
    splitter and merger prefer to use the top priority … Figuring out how things split/merge is a
    surprisingly hard problem and this mode may slow down greatly for larger builds."
  - The Manual calculator "is very fast and will probably be near instantaneous except for
    extraordinarily large builds".
  - The devlog also defends "everything goes to zero" as a deadlock signal: "this is not a bug, it
    is a feature".
- **Devlog, 2024-11-02** [observed]: "If all connections between two sections have an overflow
  like this, the algorithm can now detect that the second section cannot backup into the first and
  thus the first section can be calculated independently … greatly improving calculation times."
  That is decomposition at backpressure-cut boundaries.
- **Devlog, 2026-01-23** [observed]: the Experimental Manual Calculator "should always run
  quickly".
- **Users** [reported]:
  - Steam thread "Any Solution to extremely long 'calculation' times?" (2024-10-08): "every time I
    change something it is taking 3-5 minutes to calculate". Workarounds offered were sending
    overflow to a sink, splitting the factory into outposts, and switching to the manual
    calculator.
  - Thread "Red Stop Button" (2025-03-15): "the back end calculations are super intense".
  - The Vaporlens aggregate of Steam reviews names "slow calculations, freezes, and crashes", "stops
    calculating at a certain number of connections" and "memory leaks". Vaporlens does not state
    its method, so treat it as a clustering of reviews.
- **The "it's Java" claim** is **unverified**. Neither the store page, the itch.io page nor a web
  search names a runtime. The itch.io files are about 50 MB per platform plus a 6.1 MB
  platform-neutral zip, which is consistent with a bundled JVM plus a jar. [inferred]
  - Whatever the runtime, minutes per change on a calculation that a 1 ms LP covers points to the
    algorithm, not the language. [inferred]

### 2.2 Recomputing only what a change affects

Ranked by how much each buys factor. All [inferred] unless marked otherwise.

1. **Solve per weakly connected component.** Foreman2 does this [observed], and so does Modeler at
   overflow cuts [observed].
   - A change dirties one component. The others keep their cached solutions.
   - ⚠ Global rows couple components: shared resource caps, one power grid, an imported shared
     intermediate. Treat each global row as an edge in the component graph, or the decomposition
     silently drops a constraint.
2. **Condense the graph into strongly connected components** for the fixed-ratio case (semantics
   1).
   - Acyclic parts propagate in topological order in O(V+E).
   - Each SCC (a recycling loop) is solved **directly** as a small linear system with sparse LU,
     never by iterating until the values settle.
   - Iterating converges geometrically at the loop's recycle ratio. A loop that returns 95% of its
     flow needs about 270 iterations to reach 1e-6 (0.95^270 ≈ 1e-6). That is a plausible source
     of slowness in any propagate-until-stable engine.
   - YAFC already uses SCCs, but for diagnostics. [observed]
3. **Run the solve off the UI thread, with a generation counter and cancellation.** FICSIT Planner
   runs HiGHS in a web worker "so solving … never freezes the UI". [observed]
   - Modeler's "STOP" button means the user waits on the solve. [observed in thread]
   - For factor: a solver thread, debounced input, and stale-generation results dropped. This
     matters more than raw solve speed for how responsive the app *feels*.
4. **Keep derived values in a dirty-tracked dependency graph.** That covers belt tier per edge,
   machine count, power, and port fit. A change touching only presentation (positions, grouping)
   never reaches the solver. This follows directly from CLAUDE.md's proposed three-layer split.
5. **Warm-start the solver.** Low value at these sizes, given §2.4.
   - HiGHS supports basis warm start in its C API (`Highs_setBasis`, `Highs_setSolution`), but the
     `highs` crate wraps only `set_solution`. [observed]
   - microlp offers `add_constraint` / `fix_var` re-solves from the previous solution. [observed,
     README]
   - Worth it only if profiling says so.

### 2.3 Solving loops directly

- **Within an LP, loops are free.** Balance rows are simultaneous equations, so a recycling loop
  (rubber and plastic, the Factorio oil cracking cycle) needs no special handling. [inferred,
  consistent with every LP tool, observed]
- **A loop with no feasible balance** shows up as infeasible (Foreman2's Kovarex comment
  [observed]), or as a nonzero elastic slack (§5).
- **In a fixed-ratio propagation engine,** solve each SCC as Ax = b (Factory Planner's Gaussian
  engine [observed]).
- **⚠ Precision on loops is a real correctness issue.**
  - YAFC issue #80 (2024-03-14) [reported]: imprecise results at 1e-6 scale in Pyanodons, where
    "YAFC says that the large part of the chain is unnecessary, which is incorrect".
  - Issue #284 [reported] traces this to `float` storage plus GLOP's tolerance relaxed to 1e-1.
  - Kirk McDonald uses rational arithmetic throughout [observed].
  - Satisfactory's data is rational (amounts ÷ seconds). An exact pass is affordable: take the
    optimal basis from HiGHS, then re-solve that square basis system in rationals. This is the
    standard exact-LP refinement technique. [inferred; not tried here]

**Conclusion, with its range stated.** The range is these synthetic and whole-database LPs, on one
M4, in HiGHS 1.15.1 through Python.
- A single Satisfactory factory re-solves in about 1 ms.
- Whole-database Space Age takes 2 ms, and Pyanodons about 0.8 s.
- A deliberately oversized 300-factory plan with binding caps takes about 0.66 s.
- So decomposition matters for keeping edits instant on very large plans, not for making them
  possible.
- Infeasible models are the expensive case, which is the measured argument for an elastic
  formulation.

## 3. Nonlinear power and modifiers

### 3.1 The maths [inferred, a derivation]

Take a recipe with base rate *k* per machine at 100%, base power *P*, clock *c* and exponent *e*.
Write *R* for the recipe's total rate.

- **Machines:** m = R / (k·c).
- **Power:**
  - P_total = m·P·c^e = R · (P/k) · c^(e−1).
  - **For a fixed c, power is linear in R.**
- **Satisfactory:** with e = 1.321929, power per unit of output grows as c^0.32. Underclocking
  saves power and costs buildings.
- **Somersloops:** output is multiplied by (1 + s/slots), and power by (1 + s/slots)². This is the
  formula in FICSIT Planner's `machinePower` and Satisfactory Logistics' post-processing
  [observed].
  - **Somersloops change the item balance**, because the same inputs give more output. So they
    belong inside the LP, as a recipe variant, not in a pass after it.
- **Integer placement breaks linearity a little.** n−1 machines at c_max and one machine at the
  remainder draw P·[(n−1)·c_max^e + c_rem^e], which is not linear in R. FICSIT Planner corrects
  this with an iterated re-charge, as below.
- **If clock is a decision variable and m is continuous:** P_total = P·R^e·m^(1−e)/k^e is the
  *perspective* of the convex function R^e, so it is **jointly convex** in (R, m). Minimising power
  plus building cost is then a convex power-cone program, with no discretisation needed. Clarabel
  supports power cones. [inferred, **untested**]

### 3.2 How the tools do it [observed]

- **FactorioLab:** overclock and Somersloop slots are per-recipe settings applied before the solve.
  Power is computed after it with `oc^1.321928`.
- **Kirk McDonald (Satisfactory):** per-recipe overclock and Somersloops. This comes from the
  prior survey `calc-tools.md` and was **not re-checked** this session.
- **Satisfactory Logistics:** per-node overclock and Somersloops as fixed LP inputs. The last
  machine is partially clocked after the solve.
- **FICSIT Planner:**
  - Fixed per-recipe clock and *average* Somersloops in the LP.
  - Then a re-charge loop of up to 4 passes: "Charge each recipe what its placement really draws
    and solve again; the counts barely move, so this settles fast."
  - Then `autoAssign`: Somersloops go "to the machines whose inputs are the most expensive in raw
    resources per slot (the solver's shadow prices)", and each step re-solves "and only sticks if
    the total stays within stock".
  - This is a greedy heuristic, not an optimum.
- **Modeler:** manual per-machine clock. "Auto Round" lowers a clock so the machine count rounds
  up to a whole number, to 4 decimal places, "the accuracy allowed in game" (2025-08-26 devlog).
- **Factorio (FactorioLab, YAFC, Helmod, Kirk):** modules and beacons are a fixed configuration
  per recipe row, applied as an adjusted recipe before the solve. Speed, productivity and
  consumption all become linear coefficients. FactorioLab's `adjustment.ts` also folds the
  Satisfactory Somersloop in as a "module".
  - YAFC chooses modules with a heuristic filler (`ModuleFillerParametersScreen.cs`), not inside
    the LP. I saw only the file name.
  - Factorio's energy is linear once the configuration is fixed. [inferred]

### 3.3 Options compared

Ranked by fit for factor. Each verdict is [inferred] from §3.1 and §3.2.

## 5. Diagnostics: infeasible plans and byproducts

What the tools ship [observed]:
- **The elastic formulation, which never shows the user "infeasible".** FactorioLab gives every
  item row surplus, unproduceable and excluded slacks with tunable penalties. The diagnosis is
  *which* slack is nonzero, named by item. "Unbounded" is traced through GLPK's ray to the recipe
  responsible (`unboundedRecipeId`).
- **Solve, then add slack.** YAFC solves strictly first. On failure it adds slack only on
  SCC-derived deadlock candidates and split links, re-solves, and flags rows. Foreman2 uses
  heavily weighted error and overflow variables and colours nodes red, gold or orange.
- **Shadow prices.** FICSIT Planner reports a per-item "marginal cost of one more unit/min" and
  uses it to place Somersloops. YAFC's `CostAnalysis` reads constraint duals across the whole
  modpack.
- **Satisfactory Factories** shows shortage and surplus states on factory chips, with no solver.
  This is from the prior survey `calc-tools.md` and was not re-checked this session, although its
  CHANGELOG line 10 does mention a "3 shortages" chip.

What a Rust solver gives you to build these [observed]:
- **Primal values of slack columns:** any backend. This is enough for the elastic pattern, which
  needs nothing special from the solver.
- **Duals and reduced costs:**
  - `good_lp`'s `SolutionWithDual`, on highs and clarabel only.
  - The `highs` crate's `dual_rows` / `dual_columns` directly.
  - Reduced costs answer "why isn't the solver using this alternate".
- **IIS and ranging:** HiGHS C API only, through unsafe highs-sys. microlp returns only
  `Error::Infeasible`.

There is also a measured cost argument [observed, §2.4]: proving a 300-copy LP infeasible took
8.9 s, against 0.47 s to solve it feasibly. A strict model fails slowly as well as unhelpfully.

My view [inferred]: lead with the elastic pattern, because it is solver-independent, a user can
read it, and it always returns a plan. Keep IIS as a developer and debugging tool behind the
interface, used when the elastic penalties themselves look wrong.

## 6. Recommended engine shape [inferred]

This is a shape, not a set of decisions. The open decisions are in §7. Every item below is
[inferred]: it is assembled from the evidence above, not tested as a whole.

1. **The core model is a game-neutral linear program over a normalised recipe matrix.** `Formula`
   becomes columns, `Unit` becomes rows, and transport, power and fuel become ordinary rows.
   - A route carrier's fuel or battery use is just another consumer column, which matches the
     CLAUDE.md proposal.
   - Per-game curves (clock exponent, Somersloop boost, module effects) are **pure functions that
     produce coefficients before the solve**, driven by the data files. They never live inside the
     solver.
2. **The formulation is elastic by default:** penalised surplus, import and unproduceable slack on
   every item row, so every edit returns a plan plus named problems.
3. **There are two front ends over one solver layer:**
   - "Plan to targets" (recipe choice).
   - "Graph the user drew" (conservation plus ratios on edges).
   - The second compiles to the same LP, with a fast path for fully determined SCCs (direct sparse
     LU).
4. **Integers come after the solve:** round the machine count up, partially clock the last
   machine, and run the re-charge loop for power. MILP is opt-in, only for stock problems
   (Somersloops and shards via option B, whole blueprint copies).
5. **Incremental recompute:**
   - Dirty-tracked derived layer.
   - Per-component solve, with global rows (caps, power grid) treated as coupling edges.
   - Solver thread with debounce, a generation counter and cancellation.
   - Warm start waits on the solve-time instrument in item 7. That instrument is the trigger, so
     the deferral can actually fire.
6. **Solver isolation:** a narrow `trait`-level boundary of your own (build model → solve →
   primal, dual, status), so HiGHS and microlp are swappable and testable against each other. Use
   HiGHS first.
7. **Correctness instruments:**
   - A rational re-check of the final basis, or at least a conservation-residual assertion on
     every solve.
   - Positive-control fixtures like the ones in `lp_bench.py` and `lp_bench_flab.py`. Derive the
     expected value from the game data, not from vanilla knowledge: the Py control shows why.
   - **Solve time recorded on every solve**: model size, build time, solve time and status.
   - **A budget test in CI** that fails when a reference plan (for example the Py whole database)
     exceeds a stated time. This is the trigger for warm start and finer decomposition, and it
     follows Peter's "instrumented at first use" value.

## 7. Decisions this leaves for Peter

None of these is decided here. Each has a recommendation attached.

- **D1. Graph semantics: conservation plus ratios, or in-game splitter behaviour?** This one shapes
  the engine more than any other.
  - Ratios and conservation are an LP, fast and well understood.
  - In-game behaviour (even split, priority, backpressure, "goes to zero" deadlock detection) is
    what Modeler's users praise **and** what makes it slow. My only route to it is an untested
    sequence-of-LPs idea.
  - *Recommendation:* ratios and conservation as the core. Treat in-game splitter simulation as
    **parked**, not deferred, because nothing would fire it automatically.
    - It comes back only when Peter decides the diagram must flag in-game deadlocks or
      uneven-split starvation, as Modeler's "goes to zero" does.
    - If he wants it, it is a separate analysis pass over a solved plan, not the core solve.
- **D2. Clock and Somersloop handling: option A only, or A plus B?**
  - *Recommendation:* A first. Add B when "optimise my Somersloop stock" is wanted, since
    FICSIT's greedy heuristic is the only shipped attempt.
- **D3. Solver dependency: HiGHS (C++ toolchain at build, MIT, fast, duals) or microlp (pure Rust,
  no duals, slower and less proven)?**
  - *Recommendation:* HiGHS behind your own trait, with microlp kept compiling as a toolchain-free
    fallback. Also decide whether to use `good_lp` or the `highs` crate directly; `highs` gives
    direct dual access and a path to raw IIS.
- **D4. Exactness: floats with a residual check, or a rational re-solve of the final basis?**
  - *Recommendation:* show rationals. Satisfactory players read "37.5/min", and the YAFC precision
    bugs are the cautionary tale.
- **D5. Default objective and penalty weights.** Options are least raw resources weighted by
  scarcity, fewest buildings, least power, or user-tunable like FactorioLab. Each changes which
  alternates the plan picks.
- **D6. Whether "plan to targets" and "graph the user drew" are one view or two.** YAFC links,
  Foreman2 nodes and Modeler canvases are three distinct interaction models over the same LP.
